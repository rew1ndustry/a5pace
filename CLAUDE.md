## Moves rule (nut, firm, fundamental)
- A gain/pan change is a **move**: an additive job on a looping tape (tank += to - from), like a head adding, and inverting to subtract. The sum is right in the end whatever the order.
- **NOW (`!`)** differs from a normal insert in one way only: it starts at the take's start and does not wait for the playback head. `from` is the existing placement, so it cancels the old insert and adds the new. It simply runs over queued jobs; it never cancels them (they must complete) and need not wait for them. Wrong-sounding in between is accepted.
- **Quit = drain.** A drain flag turns the wait logic off (every move runs like NOW); the core keeps ticking until nothing is queued, then closes. Never drop moves at close.
- **No dirty tank, no rebuild, ever** in aspace or its core. Only a catastrophic crash leaves a tank unclean. Keep an SQL list of moves in progress (take, from, to, last tick written); empty once drained; after a kill, resume from it. A last-resort `a5rebuild` utility is allowed, outside the core.
- Safe mode must never touch queued moves.
- **Chip model (design agreed 2026-11-08, branch `moves-drain`, not built yet).** The tank is chips of one tick, each with its own full header (iteration, pass, output gain/peak, seq, session): no tank header, never seek in the loop, read it as a stream. Iterations on disk either all match or drop by exactly 1 at one edge (the restart point; all equal = start at the top); anything else is a corrupt loop (`a5rebuild`, outside the core, also converts old tanks). Each tick: read the next chip, check it against the output gain (clip: slope the gain down over the chip being played, reusing the `asp_mix_out` fade; add a `GAINRESET` call; gain starts from the last-written chip), play, apply every queued job in any order to the chip under the record head, stamp the header, write that chip in one call. (Superseded 2026-11-09, see Status: jobs edit the front chip and are heard within a tick; only the live feed edits behind the playback head.) **The window supersedes "play chip k then edit chip k" (nut, firm, 2026-11-09):** the core keeps a window of chips in memory, the front one read ahead (for the gain slope), the back one under the record head, which is `latency` behind the playback head. One read at the front and one write at the back per tick, on separate forward-only handles (`rf`, `wf`): no seeks but each handle's own wrap. All jobs and the live feed of the open take edit the chip under the record head, in memory, so there is no other tank access (no random get/put in the tick, no live-feed buffer). A chip is written one tick after the record head leaves it, so a pre-roll can still reach back into it. Latency is not a whole number of ticks: the output tick straddles two chips, so the gain lookahead checks the peak of every chip the next output tick touches (it may start the slope up to one chip early: safe). The window is about `latency/TICK + 3` chips (~1 MB for a 1 s round trip). (Partly superseded: a normal job still waits for the take's start chip, but it is the *output* that must reach it; NOW at the chip being played.) A kill loses edits in chips not yet written: the SQL progress row is the last chip *written*, and the resume redoes the rest. Resync or an edge drop flushes and rebuilds the window; the sync phase does not touch it. Takes/moves in progress are rows in SQL (take, from, to, position and pass of the last chip written); empty when drained; compare with the edge after a kill, allowing that the last chip may have been written before its row was updated.
- **Jobs and flac.** Take files are stream-encoded and read forward only. A job stacks the file offset of each tick as it streams (tell callback, no SQL offsets), then seeks (lseek + `FLAC__stream_decoder_flush`) to the stacked offsets on later laps; N decoders if that fails. (Superseded: neither waits for the take's start.) Normal jobs run first; only one immediate job runs at a time, the other immediates queue. **Budget (corrected 2026-11-09, supersedes the earlier "a job out of time carries on next tick"):** a job that has started is on the SQL list as in progress and every chip it covers must get it, so a running job is never cut short or skipped; all overlapping insertions that apply to the chip complete. The per-tick limit (command-line option, default 4/5 of a tick) only decides how many *not yet started* jobs begin this tick. If the running jobs alone exceed the budget the tick overruns, which is accepted. Write this model into the comments at the top of `aspace_main.c` when it is built.
- **One read, one write per tick (nut, firm).** Each tick reads the tank once and writes it once, in whatever order of read / update / write is tidy; no seeks, no other tank access, no loop file header at all. On drain the core just stops waiting for the audio I/O and reads/writes as fast as the system allows.
- **Only started jobs are listed.** A pending job (never wrote a chip) is not in SQL and is forgotten after a kill; the row is created when the first chip is written, deleted when done. **A take's stored state is its state before the job began (nut, firm, settled 2026-11-09):** the change in progress lives in the jobs list (from/to); the stored state becomes `to` only when the job completes. A forgotten pending job therefore leaves state and tank both at the old values. The current `change()` in `aspcore.c` writes the new state at queue time: old-model code, to be changed to write at completion (to-do 1).
- **Load.** The event message (log) should carry the tick load (time used against the budget) so overruns can be watched; when the chip model is done a5hell shows the load and the current gain.

## Gain rule (nut, firm)
- Gain, pan and the sync tone are **bit shifts only**: no dB, `pow`, `log`, multiplies in anything that changes a sample. Shell `+N` = left shift N bits (louder, saturates), `-N` = right shift (quieter); pan `/N` right, `\N` left = the far side shifted N more. Field `gsh` (was `gdb`); `asp_place_shifts` is the one place it becomes tank right-shifts. `--level N` on a5click/import/create stays a right shift. One bit is about 6 dB, only ever said in prose.
- The smooth output fade in `asp_mix_out` is deliberate: leave it. Real gain maths belongs to future envelopes only. Meters/peaks/gate/a5tune keep their dB measurement maths (they only read levels).
